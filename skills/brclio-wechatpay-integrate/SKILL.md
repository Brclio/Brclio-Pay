# Brclio Pay · 仅微信接入

为当前任务指定的一个产品完成服务端下单、收银台跳转、验签回调、幂等权益开通和客户端状态更新，或最小修改该产品已经登记的支付配置。通用 Skill 不包含凭证；当前任务的临时接入令牌仅对一个产品及指定新增/修改操作有效，通常两小时后到期。

如果只有复制来的任务提示词、没有附件，用其中的支付中心地址请求 `GET /api/skills/brclio-wechatpay-integrate.zip`，公开通用包不需要授权；随后 context/plan/apply 通过 `Authorization: Bearer …` 传递临时令牌。下载到当前任务专用、被 Git 忽略的临时目录后解压，读取包内 `SKILL.md`、引用文档并运行其中的 CLI。不要把令牌放进 URL/query、打开 verbose 请求日志，或自动安装到全局 Skill 目录；用户要求全局安装时再执行安装。

## 本 Skill 的支付范围

本次接入范围为 **仅微信**。登记或更新平台配置时写入 `providers: ['wechat']`，不扩展到用户未选择的渠道；已有平台从 context 的当前配置和版本开始，仅按这次明确的支付范围调整 providers。产品后端下单传 `provider`，取值为 **wechat**；核对返回 `order.provider` 并保存到业务订单。历史平台未设 providers 时仅开放支付宝，省略 provider 的下单兼容支付宝；微信单渠道必须显式传 `wechat`。

支付宝支持 `page`（电脑网站）/`wap`（手机网站）；微信仅支持 `native` 扫码。先读取签名目录 `providers/channels`，只呈现服务端当前启用的渠道。支付订单固选 provider；同一业务订单幂等重试不能改 provider，要改支付方式需用新业务订单号并处理原付款窗口，避免重复收款。

网页、桌面和移动客户端统一打开外部 HTTPS 收银台。支付宝跳转官方收银页；微信在收银台生成二维码，用户用微信扫一扫，手机同屏可提示另一设备扫码。本服务没有微信 JSAPI/H5/App SDK、支付宝原生 SDK 或保证客户端自动前置的能力。不得伪造已开通能力、索取公众号 openid 或把 Native 误接成 App 调起。

## 先确认范围，再接入

临时授权允许读取、生成计划及应用**指定产品**的 Brclio Pay 配置，不允许修改其他产品，不提供管理员密码、支付宝/微信商户私钥或 GitHub 令牌。它不替代用户对目标产品仓库的访问、编辑和部署授权；仅在当前任务已授权的仓库及工作范围内行动。用户已明确要求接入或更新时，可继续完成该范围内的计划和应用，无须重复征求确认。

1. 从任务上下文取得产品 ID、新增或修改操作范围、支付中心地址、授权到期时间及 `brp_int_…` 临时令牌。支付环境从 context.paymentMode 核实，`mode: create/update` 是接入操作类型，不是正式/沙箱环境。将令牌仅放入当前进程的 `BRCLIO_PAY_INTEGRATION_TOKEN` 环境变量，不写入 Skill、源码、计划文件、日志或提交。不要把它作为命令行参数或输出凭证。
2. 对目标仓库运行 `node scripts/inspect-platform.mjs /绝对路径/产品仓库`，再读取有关业务源文件。扫描器只输出路径、能力标签及候选套餐证据行号，不读取 dotenv、私钥、凭证文件，不输出源代码或价格值；候选位置不是已经证实的套餐。先识别用户认证、业务订单、价格、权益存储、已有支付提供方与 webhook 处理，再决定接入位置。保留已有行为，避免另建一套不关联用户的演示订单。
3. 读取 [接入协议](references/integration.md)，运行 `node scripts/integration-client.mjs context` 获取实际产品配置和版本。版本为 `context.client.version`，新产品为 `absent`；context 同时包含 `domainMode`、`pricingMode` 与 `allowedOrigins`，按下述域名模式处理。工具默认隐藏凭证；只有用户任务需要在目标后端落地 Secret 时，才使用 `context --credentials-file /已被Git忽略的路径/.env.brclio-pay` 写入已存在产品的凭证。新产品在 apply 后才产生凭证，可使用 `apply PLAN_ID --credentials-file /已被Git忽略的路径/.env.brclio-pay`。文件独占创建且权限为 0600；不要覆盖既有 Secret 文件。

## 商品来源：读取项目或人工指定

任务中的 `pricingMode` 与 create/update、live/sandbox 无关。没有指定时使用 `detect`。

- **detect：读取项目现有套餐。** 从扫描器的 `catalogCandidates` 定位后端商品配置、套餐数据结构/迁移及定价文档，并实际阅读相关代码。已有只读数据库权限时，只查询必要的商品/套餐记录，不导出客户、订单或凭证。以前述业务依据确认 SKU、金额、币种、权益及有效期，再和前端定价页核对。本中心只有 CNY；不能把 USD 等外币金额照抄为人民币，也不能自行换汇，需用户给出明确的人民币收费规则。报告路径与行号或脱敏的查询出处、商品映射和待确认项；前端文案、测试夹具、旧注释或依赖锁文件不能单独作为真实收费依据。若后端、数据库和文档互相冲突，先问用户，不替其选价。
- **manual：人工指定规则。** 使用用户在当前任务明确给出的真实商品、价格、权益及有效期；仍检查旧套餐和订单逻辑，避免重复 SKU 或影响已有付费用户。用户明确指定的规则优先于项目旧展示；发现关键差异时报告，并同步调整目标产品。缺少必要业务规则就问用户，不补造金额或权益。

两模式都先生成商品对应关系，再提交计划。目录 SKU 必填 `subject`（名称）与 `amount`（人民币两位小数字符串）；可选 `enabled`（默认 true，false 停售）、`description`（最多 500 字）、`entitlement`（最多 1000 字，说明权益与有效期）。`entitlement` 是说明，实际开通规则仍由目标产品后端维护。已有平台更新保留未请求修改的商品字段。

## 域名来源：自动发现或固定范围

来源只包含 `https://`、host 与可选端口；具体 webhook/返回页路径可以根据目标项目路由自行设计。例如来源 `https://xhs.download.brclio.com` 可使用 `/api/payments/brclio/webhook` 和 `/billing/return`，不需要为每条路径另加授权。

- **`domainMode=auto`：** 用户允许 AI 为**指定产品**自动发现或设计所需的公网 HTTPS 来源。先检查该项目实际域名、部署与后端路由，再把必要的新来源连同配置提交 plan；核对 `addedOrigins`、回调和返回页后按当前任务授权应用，无需逐个要求用户再次签发。来源在 apply 时纳入该授权记录，管理员可在后台查看实际平台域名及授权记录。不要虚构已部署的域名、改动 DNS 或申请新域名来使配置通过，也不要为省事引入无关或过宽通配来源；缺少目标项目部署权限时仍需说明阻塞。
- **`domainMode=fixed`：** 新增或变更地址必须在 `context.allowedOrigins` 中。只有管理员显式授权的通配来源允许其匹配的子域名；不同 host 不会自动获得权限。需要额外后端 host 时列出完整来源，请管理员补充并重新生成任务。

旧授权未带 `domainMode` 时按 fixed 处理。两种模式都限一个产品、最长两小时、可撤销，不能访问其他产品或扩大目标仓库权限。`pricingMode` 以 context 返回值为准，旧授权缺省 detect。

## 新产品与已有产品

本次接入登记 `config.webhookProtocol: "brclio-v1"`，使用本包的统一 `payment.paid` 事件与 `timestamp + '.' + rawBody` HMAC。新产品缺省协议也是 brclio-v1。

如果 context 显示已有平台为 `wechat-legacy-v1`，这是正在使用的旧微信回调协议，不能直接改配置再开发接收端。先在目标产品实现、部署并验证新协议 webhook，同时保留旧端或让同一端兼容旧签名/事件；随后才 plan/apply 切换 `webhookProtocol`。已签发 outbox 的协议与外部产品 ID 已固定，旧事件仍会按旧格式重试，不会因这次更新变成新事件；过渡接收端须继续幂等接受它们，两个协议映射到同一业务订单及权益事务。不能为适配协议重新生成长期凭据、回滚已开通权益或重发一份新权益事件。已有平台原配置没有此字段时，先读取实际 context；不要把遗留迁移标记当成可删除的废字段。

- **新产品：** 根据真实业务 SKU、固定金额、公开 HTTPS webhook 和返回 origin 生成配置；创建时使用 `expectedVersion: "absent"`。产品 ID 必须等于授权目标。
- **已有产品：** 以 context 返回的当前配置和版本为基线，只修改用户要求的字段。保留未请求变更的 SKU、返回域名、回调和启用状态；不旋转凭证，不重置其他支付提供方。版本冲突后重新读取并合并一次；仍有冲突、目标不符或授权过期时停止相关应用，并说明所需的新授权或业务决定。

将完整的目标配置及 `expectedVersion` 写入**不含凭证**的 JSON 计划文件，运行 `node scripts/integration-client.mjs plan /路径/plan.json`。比较返回的 `before` 与 `after`，检查目标产品、环境及有效期，再用 `node scripts/integration-client.mjs apply PLAN_ID` 应用这个计划。计划以版本比较防止覆盖并发更新；不要绕过计划、伪造版本或扩大令牌权限。

商品改价只作用于之后创建的订单，历史订单金额保持原值。改价或改权益前，检查目标产品是否用当前套餐金额校验旧通知；同步安排目标产品展示、购买资格、下单校验与订单快照，不能让新支付金额被产品旧价格拒绝，也不能用新权益覆盖旧订单承诺。更改 webhook 会影响尚未投递的付款通知；必须确认新接收端已就绪、保留旧端过渡或说明未处理通知的影响。停用商品/产品只阻止新购买，已有订单继续验签、查单和开通；不要删除业务记录。

## 产品后端实现

按实际框架适配 [服务端客户端模板](assets/payment-client.mjs) 与 [回调模板](assets/webhook-handler.mjs)，不要把 Node 专用文件直接打包到浏览器或移动客户端。其他语言实现相同协议即可。

- 实现产品后端通过长期 API Secret 签名读取 `GET /api/v1/catalog`（模板 `pay.catalog()`）。校验所属产品、mode、providers/channels 与 `currency=CNY`，通过产品自己的后端向网页/客户端提供公开商品；不把支付 Secret 发给前端。展示与下单读取启用商品，不缓存或设置明确短缓存，避免把价格固化在静态构建里。已实现目录读取的产品可读取后台新价；旧产品须先完成这次改造。`acceptingPayments=false` 时保留报价、旧单查单和通知处理，暂停新购买并显示收款未开放；刷新目录恢复。目录检查后仍可能返回 `PAYMENTS_DISABLED`，按固定脱敏提示处理并保留原业务订单，不盲目重试。兼容旧服务缺少此字段，不能把目录可读当成已开放收款；商品版本不因开关变化而改变。
- 用户由原产品登录态认证，业务后端根据商品与购买资格创建业务订单，保存付款订单与用户关联，并快照该笔订单的 SKU、金额、实际权益规则及有效期。`createOrder` 响应的 SKU/amount 是当笔支付订单权威。读取目录和下单之间可能改价：若响应与用户已确认报价不同，停止放出 checkoutUrl，让用户确认新报价后用新业务订单重建；不能暗中涨价或继续按旧价验签。权益说明仅是文案，实际产品开通规则仍须实现并同步修改。
- 首次付款期限为创建后 10 分钟，未重开的旧单同样按原创建时间计算；到期禁止发起付款。重复创建不会延长期限，产品普通重购使用新业务订单号。只有管理员可在后台核实后为已关闭原单新建支付尝试和 10 分钟窗口，保留原中心/业务订单 ID、金额与权益依据；产品 API 和临时 AI 授权不能重开。以接口当前 `expiresAt` 为付款期限，不从原创建时间推算重开期限。中心定时或主动刷新会先核实上游付款/关单状态，异常时可能暂为 `PENDING`，产品不能把到期 `PENDING` 视为仍可付款。已发出的支付宝链接不能追溯改写期限，提前关闭后仍可能有尚未创建交易的旧链接可付，后台在旧窗口未解除前拒绝重开。`CLOSED` 后保留迟到有效付款和管理员验签补记的幂等履约路径；事件 ID 仍固定归原逻辑订单，不能因业务侧已过期而拒绝真实付款通知。
- 网页、桌面、Android 与 iOS 打开支付中心的外部 HTTPS 收银台；前端或安装包不保存 API/webhook Secret。原生支付宝 SDK、深链自动回跳需要独立实现与验证。
- webhook 先验签、校验环境、所属产品、业务订单、provider、SKU、金额，再在同一持久化事务内去重事件、开通权益并更新业务订单。重试同一事件应返回成功；不能用内存 Set 作为生产去重表。
- HTTPS 返回页只携带订单引用。产品后端查单确认状态；回跳参数、客户端“成功”提示都不能开通权益。沙箱事件只能用于测试，正式权益接收端默认拒绝它。

## 完成付款后的客户端同步

不能把“打开付款页”“中心已 PAID”或“回调已送达”作为接入完成。产品自己的已认证查单接口应分别返回付款状态和**该业务订单实际已提交的权益状态**，校验当前用户归属，不能只拿账号原本已有的会员资格代替这笔订单的履约证据。

- 下单成功后保留当前用户与业务订单的关联，网页返回、桌面窗口 focus、移动应用 resume 时立即查询产品后端；等待付款时也进行有界低频查询。`PAID` 但权益未确认时继续等待，不停止在“已付款，稍后查询”。可按 [完成状态模板](assets/payment-completion.mjs) 适配已有框架；这是调用产品后端的无密钥客户端模板，不是签名 SDK。具体响应映射见 [接入协议](references/integration.md)。
- 产品后端确认该订单实际权益提交后，重新获取账号/权限，更新会员标识、到期时间和功能权限，关闭或更新付款弹窗。客户端等待超时不等于服务端订单已关闭，保留订单与手动查询，不提示重复付款；收到 `CLOSED` 时停止本轮等待，用户普通重购时新建业务订单并保留旧单查证。管理员为原单重开后，用户须重新打开收银台或恢复手动查询，不能承诺旧客户端自动恢复。隐藏时暂停，离开/退出/切换账号时清理请求和监听，忽略旧账号迟到结果。重启后从该用户的业务订单恢复，不能只依赖组件内存。
- 支付中心会在 live 订单通知送达后倒计时返回已登记 HTTPS 页面；这不保证桌面应用被操作系统拉回前台。没有已验证的 App Links / Universal Links 或产品自己的安全唤起方案时，以应用回到前台查单作为必需路径，不把新增自定义 scheme 当作支付凭据。

测试应覆盖付款晚于回跳、PAID 后回调延迟、10 分钟到期禁止付款、关闭后以新业务订单重购、旧单迟到有效付款仍幂等履约、外部浏览器返回桌面、隐藏/恢复、账号切换、等待超时手动恢复，以及重复回调只开通一次。使用假的上游支付和测试订单，不自行执行真实付款。

## 在产品项目完成上线与开放

任务已授权接入、部署并开放收款时，继续在**产品项目**完成后端 Secret 配置、webhook/查单/返回页和网页或安装包发布，再核实线上目录与实际路由；不能停在中心 plan/apply 成功。新建产品可在计划中使用 `enabled:true`；已有产品保留启用状态，除非本次任务明确授权恢复收款。上线前用产品自己的功能开关限制尚未完成验证的购买入口，避免公开一个无法履约的入口。

当 `/api/health` 的 `ready/acceptingPayments` 和产品签名目录的 `enabled/acceptingPayments` 均为 true、环境正确且商品可售，完成产品检查后即可按当前授权开放该产品入口，**不需要返回支付仓库再次部署或改总开关**。签名目录才反映该产品是否允许收款，不能仅凭公共 health 判断。总开关 false、商户权限缺失或外部发布权限不足时，明确指出具体阻塞；临时产品授权不能修改总开关或商户配置。固定来源不足、授权到期/撤销或操作类型不符等情况需要新的受限授权，不索取全账号凭证。create 授权成功创建后，只能重放原计划；之后若要修改回调、来源或商品，需要 update 授权，即使原 create 令牌尚未到期或允许 auto 来源。部署前先确认路由与商品，减少这类返工；令牌到期不影响已交付的长期凭证和正常支付。

部署与人工实付验收按当前用户授权进行；让用户在产品项目亲自完成一笔小额付款后，核对中心付款、回调以及产品实际权益和客户端显示。不能自动点击付款，不能把模拟测试写成真实到账。对需要安装包的产品分别报告源代码、后端、网页、安装包发布与安装后行为；网页发布不会更新用户已安装的旧前端。
